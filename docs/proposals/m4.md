## 1. Table `app.customers` (all columns AUTO-DECIDED — needs founder review)

| Column | Type / rule |
| --- | --- |
| `id` | uuid PK |
| `org_id` | uuid NOT NULL FK organizations; immutable |
| `display_name` | text NOT NULL, 1–120 chars after trim |
| `phone_e164` | text NULL, CHECK `^\+[1-9][0-9]{7,14}$`; **not unique** (shared household phones) |
| `address` | text NULL, 1–500 chars after trim |
| `acquisition_source` | text NOT NULL DEFAULT `PRIEST_DIRECT`, CHECK in (`PRIEST_DIRECT`, `IMPORT`); immutable (ADR-012) |
| `erased_at` | timestamptz NULL (set by erasure in M12; erased customers are hidden and cannot be edited) |
| `version` | int NOT NULL DEFAULT 1, bumped by `tg_bump_version` |
| `created_at`, `updated_at` | |

UNIQUE `(id, org_id)` (for the composite FK from bookings in M6). Indexes (spec §04 §6):
`(org_id, lower(display_name) text_pattern_ops)` for prefix search and `(org_id, phone_e164) WHERE phone_e164 IS NOT NULL`.
ENABLE + FORCE RLS. Trigger `tg_customer_source_immutable`: changing `acquisition_source` or `org_id` → PD422
`IMMUTABLE_FIELD` with `details.field`.

- **AUTO-DECIDED:** no free-text `notes` on customers (the spec lists name, phone, address as customer data; notes
  live on bookings).
- **AUTO-DECIDED:** only `PRIEST_DIRECT` is reachable in P0 (no import feature); `IMPORT` is allowed by the CHECK for
  later.

Policies: `app_runtime` SELECT `T`; `app_domain` SELECT, INSERT, UPDATE `T` (USING and WITH CHECK). Grants: runtime
SELECT; `app_domain` SELECT, INSERT, UPDATE (table-level, the trigger guards immutable columns, as in the spec's
`05 › customer acquisition_source is immutable` test). No DELETE for anyone (erasure is an UPDATE, M12).

## 2. Commands (owner `app_domain`, SECURITY DEFINER, `search_path = ''`)

`app.create_customer(p_display_name text, p_phone_e164 text, p_address text, p_idem_key text, p_request_hash text) → jsonb`

`app.update_customer(p_customer_id uuid, p_expected_version int, p_patch jsonb, p_idem_key text, p_request_hash text) → jsonb`

Pattern (CLAUDE.md recipe): `assert_permission('CUSTOMER_WRITE')` (PD401/PD404/PD403) → `_idem_begin` → (update:
lock the row `FOR UPDATE` under RLS; missing or erased → PD404 `details.resource = customer`; version mismatch →
PD409 `details.current_version`) → validate (PD422 with `details.field`) → write → `_idem_finish`.

`p_patch` keys: `display_name`, `phone_e164`, `address`; JSON `null` clears the two optional fields; any other key →
PD422 (`acquisition_source` → `IMMUTABLE_FIELD`). An empty patch → PD422.

Result (both): `{customer: {id, display_name, phone_e164, address, acquisition_source, version, created_at,
updated_at}, possible_duplicates: [{id, display_name}]}` plus `idempotent_replay`. `possible_duplicates` lists other
non-erased customers of the same organization with the same phone (both are saved; the UI shows a warning).

- **AUTO-DECIDED:** PATCH body is applied as a JSON patch so "absent" and "null" differ.
- No `booking_events`/`audit_log` rows: the spec's audit events do not include customer create/update.

## 3. API (all shapes AUTO-DECIDED — needs founder review)

| Route | Permission | Notes |
| --- | --- | --- |
| `GET /customers?q=&limit=&cursor=` | CUSTOMER_READ (every role; membership probe) | `{data: Customer[], next_cursor}`; sorted by `lower(display_name), id`; `limit` 1–100 (default 50); cursor = base64url of `[lower(display_name), id]` |
| `POST /customers` | CUSTOMER_WRITE | body `{display_name, phone?, address?}`; `Idempotency-Key`; `201` + `ETag` |
| `GET /customers/{id}` | CUSTOMER_READ | `Customer` + `ETag`; erased or other tenant → 404 |
| `PATCH /customers/{id}` | CUSTOMER_WRITE | `If-Match: "<version>"` required (missing → 422 `IF_MATCH_REQUIRED`); body `{display_name?, phone? \| null, address? \| null}`; `Idempotency-Key`; `200` + `ETag` |

Search `q` (trimmed, ≤ 60 chars):
- if it normalises to an Indian E.164 number → exact phone match;
- else if it has ≥ 4 digits and nothing else → phone contains those digits;
- else → **any word** of the name starts with `q` (case-insensitive), so "Sha" finds "Ramesh Sharma".
- **AUTO-DECIDED:** word-prefix rather than whole-name prefix (the plan's check "Sha finds Sharma" fails for
  "Ramesh Sharma" otherwise). The leading-word case uses the prefix index; other words scan the organization's
  customers, fine at P0 volume (spec §04 §6).

Phone input (`src/domain/phone.ts`, used by the API and the form): spaces, dashes, dots and brackets ignored;
`+…` kept (8–15 digits); `00…` → `+…`; 10 digits → `+91…`; `0` + 10 digits → `+91…`; `91` + 10 digits → `+91…`;
anything else → 422 `field: phone`.
- **AUTO-DECIDED:** landlines with STD code are accepted the same way (e.g. `0172 2345678` → `+911722345678`).

## 4. UI (Hindi first, 360 px, 44 px targets)

- Header navigation for signed-in pages: Home, Customers.
- `/customers`: search box (GET form, works without JavaScript), results (name, phone), "Load more" with the cursor,
  "Add customer" (only with CUSTOMER_WRITE).
- `/customers/new`: name, phone (optional), address (optional); one Idempotency-Key per form; after saving, opens the
  customer.
- `/customers/{id}`: details; "Other customers with this phone" warning box when there are any; edit form (only with
  CUSTOMER_WRITE) that sends `If-Match`; a `VERSION_CONFLICT` shows "Someone else changed this first. Reload the page."
- The current practice is the `pd_tenant` cookie (M2), sent as `X-Tenant-ID`.

## 5. Tests (AUTO-DECIDED — needs founder review)

Domain: phone normalisation (mobile, landline, +91/0/91/00 forms, invalid); cursor round-trip incl. Devanagari names
and tampered cursors; Zod schemas reject unknown fields and invalid phones.

SQL (`04_customers.sql`): create as OWNER/STAFF, READ_ONLY → PD403, forged tenant → PD404, missing context → PD401;
no phone allowed; same phone twice → both saved, `possible_duplicates` lists the first; invalid E.164 → PD422;
idempotent replay and key reuse; update bumps version, stale version → PD409 with `current_version`; patch null clears
phone; unknown key / `acquisition_source` → PD422; other tenant's id → PD404; erased → PD404; tenant B sees only its
own customers; runtime cannot INSERT/UPDATE customers (42501); even `app_domain` cannot write into another tenant
(42501 RLS) or change `acquisition_source`/`org_id` (PD422 `IMMUTABLE_FIELD`).

Integration: list/search by word prefix and by phone, keyset pagination over 3 pages, create → 201 + ETag + duplicate
warning, GET → ETag, PATCH with stale `If-Match` → 409, without → 422, READ_ONLY POST → 403, other tenant → 404.
