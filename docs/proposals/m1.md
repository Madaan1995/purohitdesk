## 2. Roles (earliest migration)

`app_runtime`, `app_domain`, `app_authz`, `app_bootstrap`, `app_freebusy`, `app_maintenance`: `NOLOGIN NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE`. `app_runtime` gets LOGIN and a password from the founder in M2.

- The migration runs `GRANT <role> TO CURRENT_USER` for `app_domain`, `app_authz`, `app_bootstrap`, `app_freebusy`, `app_maintenance`, so the migration user can hand function ownership to them (spec U1; PostgreSQL requires membership in the new owner). Spec risk U1 applies: if Supabase refuses any of these statements, stop and send the exact error.
- **AUTO-DECIDED — needs founder review:** plain `CREATE ROLE` (not "if not exists"). Re-running the migration on a database where the roles exist fails loudly instead of silently keeping roles with unknown attributes.
- `REVOKE ALL ON SCHEMA app FROM PUBLIC`; `USAGE` on `app` for the six roles only. If Supabase's `anon`, `authenticated` or `service_role` exist, the migration revokes every privilege they have on schema `app` (Data API must stay off for `app`).

## 3. Shared helpers (earliest migration)

| Function | Kind | Behaviour |
| --- | --- | --- |
| `app.current_actor_id() → uuid` | SQL, STABLE, invoker | `nullif(current_setting('app.actor_user_id', true), '')::uuid` |
| `app.current_tenant_id() → uuid` | SQL, STABLE, invoker | same for `app.tenant_id` |
| `app.raise_error(p_sqlstate text, p_reason text, p_details jsonb DEFAULT '{}')` | PL/pgSQL, invoker | `RAISE EXCEPTION USING ERRCODE = p_sqlstate, MESSAGE = p_reason, DETAIL = p_details::text`. Only PD-class SQLSTATEs are accepted (anything else raises PD500 `BAD_ERROR_CODE`). |
| `app.is_valid_timezone(p text) → boolean` | SQL, STABLE, invoker | `UTC` or `Area/Location[/…]` form **and** present in `pg_timezone_names`; `IST`, `EST5EDT`, `posix/…` rejected |
| `app.tg_bump_version()` | trigger | `NEW.version := OLD.version + 1; NEW.updated_at := now()` |
| `app.tg_touch_updated_at()` | trigger | `NEW.updated_at := now()` (non-versioned mutable tables) |
| `app.tg_append_only()` | trigger | any UPDATE/DELETE → PD405 `APPEND_ONLY` (attached to tables from M5/M6 on) |
| `app.tg_validate_timezone()` | trigger | the column named in `TG_ARGV[0]` must pass `is_valid_timezone`, else PD422 `VALIDATION_FAILED` with `details.field` |

- **AUTO-DECIDED — needs founder review:** error shape in PostgreSQL. SQLSTATE carries the class (`PD401`, `PD403`, …, mapped to `code` by spec §11 §3); the message is the reason (`CONTEXT_MISSING`, `VALIDATION_FAILED`, `IMMUTABLE_FIELD`, …); `DETAIL` is our JSON (`{"field": …}`, `{"permission": …}`, `{"resource": …}`). This matches the error lines in the spec's test catalog (e.g. `PD401 CONTEXT_MISSING`).
- **AUTO-DECIDED — needs founder review:** `app.tg_touch_updated_at` is an addition not named in the spec (shared trigger family), to keep `updated_at` correct on tables without `version`.
- All helper EXECUTE rights are granted explicitly; `REVOKE EXECUTE ON ALL FUNCTIONS IN SCHEMA app FROM PUBLIC` at the end of each migration (spec defect #1).

## 5. RLS, policies and grants

ENABLE + FORCE RLS on `app_users`, `organizations`, `org_members`, `priest_profiles`, `organization_priests`. ENABLE (not FORCE) on the two global reference tables `role_permissions`, `ceremony_types`, so the migration owner can seed them (spec §04 §8).
- **AUTO-DECIDED — needs founder review:** plan M1 says "RLS forced on every table"; the spec says forced on every tenant/identity table and only enabled on the two reference tables. I followed the spec; the tests check exactly that.

Tenant predicate `T` = `org_id = (SELECT app.current_tenant_id()) AND (SELECT app.current_member_role()) IS NOT NULL`. Every policy is `TO <role>`; none to PUBLIC.

| Table | `app_runtime` | `app_domain` | `app_authz` |
| --- | --- | --- | --- |
| `role_permissions`, `ceremony_types` | SELECT `true` | SELECT `true` | SELECT `true` (role_permissions only) |
| `organizations` | SELECT `app.is_active_member_of(id)` (tenant switcher, no tenant needed) | SELECT same | — |
| `org_members` | SELECT own rows (`user_id = actor`) or `T` | SELECT same | SELECT own rows |
| `app_users` | SELECT own row, or users who are members of the current tenant (subquery on `org_members`, itself under RLS) | SELECT same | — |
| `priest_profiles` | SELECT own row, or profiles linked to the current tenant | SELECT same | SELECT own row |
| `organization_priests` | SELECT `T` | SELECT `T` | — |

Grants: SELECT only, matching the policies. **No role gets INSERT/UPDATE/DELETE in M1**: M1 has no command functions. M2 adds the write policies and grants (to `app_bootstrap` and `app_domain`) in the same migration as the functions that need them.
- **AUTO-DECIDED — needs founder review:** write policies arrive with the functions that use them (M2), not in M1.

## 6. Membership helpers (owner `app_authz`, SECURITY DEFINER, `SET search_path = ''`)

| Function | Behaviour |
| --- | --- |
| `current_member_role() → text` | role of the actor's ACTIVE membership in the current tenant, else NULL (NULL when either setting is missing) |
| `current_member_has(p_permission text) → boolean` | `current_member_role()` has the permission in `role_permissions` |
| `is_active_member_of(p_org uuid) → boolean` | actor has an ACTIVE membership in `p_org` |
| `current_priest_profile_id() → uuid` | the actor's own priest profile id, or NULL |
| `assert_permission(p_permission text) → void` | missing actor or tenant → PD401 `CONTEXT_MISSING`; not an active member → PD404 `NOT_FOUND` (`details.resource = "organization"`); unknown permission name → PD500 `UNKNOWN_PERMISSION`; role lacks it → PD403 `FORBIDDEN` (`details.permission`) |

EXECUTE: `app_runtime` gets `current_actor_id`, `current_tenant_id`, `current_member_role`, `is_active_member_of` (used by its policies). It does **not** get `assert_permission`, `current_priest_profile_id` or `current_member_has` (spec defect #9: only endpoint functions or functions its policies use). `app_domain`, `app_bootstrap`, `app_freebusy`, `app_maintenance` get all helpers.
- **AUTO-DECIDED — needs founder review:** `current_member_has` is withheld from `app_runtime` until a runtime policy needs it (the `audit_log` policy in M5).
