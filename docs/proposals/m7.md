## 1. Database (migration `20261101200000_m7_reschedule_buffers.sql`)

### Travel buffers in `_reserve_booking` (spec §05 §3)
`_reserve_booking(p_booking_id, p_ack_buffer_overlap boolean) RETURNS integer` replaces M6's one-argument version.
After the ceremony check (unchanged, `23P01 BOOKING_CONFLICT`):
- **BUFFER** conflicts come from `_priest_conflicts` (M6, unchanged): another ACTIVE span overlaps this booking's
  buffered span, or another booking's buffered span overlaps this ceremony. Calendar blocks count too (their buffered
  span is the block itself) — **AUTO-DECIDED**.
- Any BUFFER conflict without the acknowledgement → `PD449 BUFFER_CONFLICT` with `details.conflicts` in the M6 shape
  (`organization_priest_id, starts_at, ends_at, same_org`, `booking_id` for the same practice only). Nothing is written.
- With the acknowledgement: `bookings.buffer_overlap_ack = true` and a `BUFFER_OVERLAP_ACKNOWLEDGED` event with
  `{conflicts: [{organization_priest_id, starts_at, ends_at, same_org}]}` (times only, no other booking's id). Without
  buffer conflicts the flag is set to false, so **a reschedule resets the acknowledgement** (spec §05 §6).
- A ceremony overlap is refused even when acknowledged (no override exists).

### `reschedule_booking` (new; owner `app_domain`)
`reschedule_booking(p_booking_id uuid, p_expected_version integer, p_changes jsonb, p_reason_code text,
p_ack_buffer_overlap boolean, p_idem_key text, p_request_hash text)`
- Permission: BOOKING_CONFIRM, or BOOKING_CONFIRM_OWN as the LEAD **before and after** any `priest_ids` change (spec
  §05 §1, R1). Checked before validation.
- CONFIRMED only (else PD410 `INVALID_TRANSITION`). Optimistic version check (PD409).
- `p_changes` keys: `starts_at`, `ends_at`, `timezone`, `is_time_tentative`, `buffer_before_min`,
  `buffer_after_min`, `priest_ids`; `local_date` is derived. Any other key (e.g. a free-text `reason`) → PD422 with
  `details.field` (spec defect 10). At least one value must change (PD422 `body`). A confirmed booking always keeps
  times and a LEAD.
- `p_reason_code` required, one of **`CUSTOMER_REQUEST`, `PRIEST_REQUEST`, `MUHURAT_FIXED`, `PRIEST_CHANGED`,
  `CORRECTION`, `OTHER`** (proposed in M6) → else PD422 `field = reason_code`.
- Releases the booking's ACTIVE reservations, writes the new schedule (and priests), then `_reserve_booking` with the
  acknowledgement. Any conflict rolls the whole transaction back: **the original slot is untouched** (AC-07).
- Event `RESCHEDULED {from: {local_date, starts_at, ends_at, organization_priest_ids}, to: {…}, reason_code,
  released}` (+ `BUFFER_OVERLAP_ACKNOWLEDGED` when acknowledged).
- Priests of a CONFIRMED booking change only here (M6 already refuses them in `update_booking`). New priests keep the
  booking's buffers unless the request sets them — **AUTO-DECIDED**.

Grants: `app_runtime` EXECUTE on the new signatures; the security-gate whitelists change accordingly.

## 5. Tests (AUTO-DECIDED)
SQL `08_reschedule_buffers.sql`: buffer-only overlap requires explicit acknowledgement (PD449, no reservation
written); acknowledged overlap recorded on the booking and in history (spans only); ceremony overlap stays a hard
conflict when acknowledged; the other booking's buffer counts too (symmetry); zero buffers and touching buffers do not
conflict; cross-practice buffer conflict has no foreign ids; reschedule into a conflict is rejected and leaves the
original reservation; reschedule releases the old slot and holds the new one (another booking can take the old slot);
RESCHEDULED event holds times and the code only; reason code required and from the list; a free-text `reason` key is
refused; DRAFT/COMPLETED cannot be rescheduled; reschedule resets the acknowledgement; change of priest moves the
reservation; PRIEST cannot reschedule another's booking or hand his own to another priest; STAFF/READ_ONLY refused;
stale version; idempotent replay; invariants hold.
Concurrency: buffer-only race across practices (second session waits, then BUFFER_CONFLICT). Founder review
(2 Nov 2026, FOUNDER-APPROVED) added, in `concurrency.sh`: reschedule vs confirm in both directions (the loser gets
BOOKING_CONFLICT; a refused reschedule keeps its original slot), reschedule into a buffer-only overlap
(BUFFER_CONFLICT, original slot kept), and multi-priest bookings with overlapping priest sets listed in opposite
orders: a staggered race, five simultaneous starts (one CONFIRMED, one BOOKING_CONFLICT, never a deadlock), and a
three-session probe proving the per-priest locks are taken in profile order (a waiter on the lower lock does not hold
the higher one; this probe fails if the locks follow the list order instead).
Integration: the plan's three checks over HTTP; reschedule replay; each reason code accepted.
Browser smoke: plan M7 checklist at 360 px.
