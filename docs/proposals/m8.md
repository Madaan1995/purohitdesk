## 1. Database (migration `20261101300000_m8_agenda_blocks.sql`)

### `priest_busy` (owner `app_freebusy`, SECURITY DEFINER; executable by `app_runtime`)
`priest_busy(p_organization_priest_id uuid, p_from timestamptz, p_to timestamptz)` RETURNS TABLE
`(reservation_id uuid, kind text, starts_at timestamptz, ends_at timestamptz, same_org boolean, booking_id uuid)`
- ORG_READ (every role); the link must belong to the current practice (else PD404 `priest`).
- `p_to > p_from` and at most **62 days** (else PD422 `field = to`).
- Every ACTIVE reservation of that human (global profile) overlapping `[p_from, p_to)`, in every practice, ordered by
  start. **Other practices' rows come back as `kind = 'BUSY'` with no reservation id, no booking id** (and no note: the
  role cannot read notes at all) — **AUTO-DECIDED** (the spec says "busy, no details"; hiding BOOKING vs BLOCK too).
  Own rows keep `kind` BOOKING/BLOCK, the reservation id, and the booking id for bookings.

### `create_block` / `release_block` (owner `app_domain`)
- `create_block(p_organization_priest_id, p_starts_at, p_ends_at, p_note text, p_idem_key, p_request_hash)`:
  BLOCK_MANAGE, or BLOCK_MANAGE_OWN when the link is the actor's own profile (spec §05 §8). End after start, at most
  **31 days**; note optional, 1–500 chars (free text on BLOCK rows only, allowed by golden rule 8). Same per-priest
  advisory lock as bookings, then **ceremony overlap only** (no buffer check for blocks, spec ADR-006) → `23P01
  BOOKING_CONFLICT`. Inserts a BLOCK reservation with `buffer_span = span`. Audit `BLOCK_CREATED` (target = reservation
  id, `data = {organization_priest_id, starts_at, ends_at}`; no note). Returns `{block, idempotent_replay}`.
- `release_block(p_block_id, p_idem_key, p_request_hash)`: same permissions; an ACTIVE BLOCK of this practice (else
  PD404 `block`); already released → PD410. Sets RELEASED (history kept). Audit `BLOCK_RELEASED` (target = block id,
  `data = {organization_priest_id, starts_at, ends_at}`; no note) — **FOUNDER-APPROVED** (2 Nov 2026; first draft: not
  audited). The migration widens M5's `audit_log` action CHECK (M5 itself is applied and not edited).
- Block rows: `{id, organization_priest_id, starts_at, ends_at, note, status, created_at, released_at, released_by}`
  (`released_by` FOUNDER-APPROVED, 2 Nov 2026).

### Conflicts with blocks (small change to `_reserve_booking`)
Conflict details gain `"block": true` for a **same-practice** calendar block, so the UI can say "पंडित जी ने यह समय
रोका हुआ है" instead of "दूसरी पूजा है". Other practices' blocks stay anonymous. `CREATE OR REPLACE` of M7's function,
same signature — **AUTO-DECIDED**.

## 2. API (AUTO-DECIDED shapes)

| Route | Permission | Notes |
| --- | --- | --- |
| `GET /availability?priest_id=&from=&to=` | ORG_READ | `from`/`to` are local dates (inclusive) in the practice's time zone, `to − from` ≤ 61 days (62 days of data); `{priest_id, timezone, from, to, busy: [{kind, starts_at, ends_at, same_org, booking_id?, block_id?}]}` |

## 3. Domain (`src/domain/agenda.ts`)
- `weekDays(localDate)`: the Monday-to-Sunday week containing the date (**AUTO-DECIDED: weeks start on Monday**).
- `localDayBounds(localDate, tz)`: `[00:00, next 00:00)` of a local date as instants (for `from`/`to`).
- `agendaItems(...)`: merges own bookings, own blocks and other practices' busy spans into one time-ordered list per
  local date; spans that cross midnight appear on each day they touch.

## 4. UI
- Header navigation: **एजेंडा** (agenda) becomes the first link.
- `/agenda` (day, default today in the practice's zone) and `/agenda?view=week`, with previous/next and "today":
  - own bookings (DRAFT with a time, CONFIRMED, COMPLETED; not CANCELLED) with time, ceremony, customer, status, ≈ for
    tentative;
  - own blocks: "समय रोका गया" + the note + **हटाएँ** (release, with a confirmation);
  - other practices: **"व्यस्त"** with the time only;
  - **"समय तय करना है"**: every upcoming date-only draft (from today), with its date.
- Block form on the agenda: date, from–to time (or "पूरा दिन"), note, priest when there are several. A conflict shows the
  busy times.
- Server-rendered; client JS only for the block form and the release button (agenda route budget ≤ 200 KB gzipped,
  measured from the build).

## 7. Founder review (2 Nov 2026) — FOUNDER-APPROVED

Made on this branch (M6/M7 items arrive by merge; see `m6.md` §9 and `m7.md`):

1. **Block over block.** M6's `_priest_conflicts` filtered `booking_id IS DISTINCT FROM p_exclude_booking`, which is
   false for every BLOCK row when `p_exclude_booking` is NULL (how `create_block` calls it). A block over a block
   therefore skipped the conflict check and hit the exclusion constraint's bare 23P01 (no `BOOKING_CONFLICT`, no
   details). The M8 migration replaces `_priest_conflicts` (`CREATE OR REPLACE`, same owner `app_freebusy` and grants)
   to exclude only the given booking. Tests: SQL (`09_agenda_blocks.sql`) block over the practice's own block →
   `BOOKING_CONFLICT` with `[{…, same_org: true, block: true}]` and nothing written; block over another practice's block
   → `BOOKING_CONFLICT` with busy time only; touching blocks allowed. Integration: `POST /blocks` over a block → 409
   `BOOKING_CONFLICT` whose conflicts make the form show `bookings.blockedTime` ("इस समय पंडित जी ने समय रोका हुआ है।",
   via `isBlockedTimeConflict` in `src/domain/booking.ts`, unit-tested). Verified: the SQL test fails without the fix.
2. **BLOCK_RELEASED audit** and `released_by` in the block read model (OpenAPI `Block`), as in §1.
3. **Races** in `concurrency.sh`: block vs booking (both directions), block vs block across practices and within one
   practice (the loser waits on the per-priest lock, then `BOOKING_CONFLICT`); exactly the winning blocks are stored.
4. `m8_checks.sql`: row 4 also checks that `app_freebusy` cannot read `organization_priest_id`; new row 6 checks the
   `audit_log` CHECK accepts `BLOCK_RELEASED`.
