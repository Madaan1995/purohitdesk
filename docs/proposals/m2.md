### Functions

| Function | Owner | Behaviour |
| --- | --- | --- |
| `app._slugify(text) → text` | migration user (invoker, IMMUTABLE) | lower-case ASCII letters/digits joined by `-`, ≤ 60 chars; `practice` when nothing ASCII remains (e.g. a Devanagari name) |
| `app._idem_begin(p_command, p_key, p_hash) → jsonb` | migration user (invoker) | NULL key → PD422 `IDEMPOTENCY_KEY_REQUIRED`; claims `(actor, key)` with `INSERT … ON CONFLICT DO NOTHING` inside the caller's transaction; on conflict: different command, hash or tenant → PD412 `IDEMPOTENCY_REUSE`, else returns the stored response with `idempotent_replay: true` |
| `app._idem_finish(p_key, p_result) → jsonb` | migration user (invoker) | stores the response, returns it with `idempotent_replay: false` |
| `app.ensure_current_user(p_locale text DEFAULT NULL, p_display_name text DEFAULT NULL) → jsonb` | `app_bootstrap` | needs an actor (PD401); existing row: refused with PD401 if the identity was deleted/detached, else returned unchanged; new row: the FK `app_users.auth_user_id → auth.users` proves the actor is an auth user (23503 → PD401; **no read of `auth.users`**, FOUNDER-APPROVED §8.2); `display_name` = `p_display_name` (from the verified JWT's `user_metadata`, untrusted display text: control and bidi-override characters → space, spaces collapsed, trimmed, ≤ 120, blank → NULL; never used for authorization); `preferred_locale` = `p_locale` if valid else `hi`. Returns `{id, display_name, preferred_locale}` |
| `app.update_my_profile(p_display_name text, p_preferred_locale text) → jsonb` | `app_domain` | NULL argument = unchanged; validation PD422 with `details.field`; returns the same shape. No idempotency key (spec §05 §9) |
| `app.bootstrap_practice(p_name text, p_ceremony_type_ids uuid[], p_idem_key text, p_request_hash text) → jsonb` | `app_bootstrap` | see below |

`bootstrap_practice`, in order: actor required (PD401); a tenant in context → PD422 `VALIDATION_FAILED` (`field: tenant`);
the actor's app user must exist, be ACTIVE and linked (PD401); per-actor advisory lock; `_idem_begin` (replay returns);
name 1–120 chars (PD422 `field: name`); 1–20 distinct ceremony ids that exist (PD422 `field: ceremony_type_ids`);
at most 3 ACTIVE organizations created by the actor (PD429 `QUOTA_EXCEEDED`, `details.limit = 3`);
insert organization (slug from `_slugify(name)`; on collision retry with a random 6-hex suffix, up to 10 tries),
OWNER membership, the actor's priest profile if none exists (one per human; name = app user's display name, else
the practice name), BOOTSTRAP link (buffers 30/30), `org_sequences` row, one offering per chosen ceremony (both
names and default duration copied). Returns
`{organization: {id, name, kind, timezone, status, version}, role: "OWNER", organization_priest_id, offering_count}`.

- **AUTO-DECIDED — needs founder review:** slug collisions are resolved automatically (suffix) instead of returning
  409, because the slug is generated and not shown (revision 2.1 #17). The spec's older test "slug already taken →
  23505" therefore no longer applies to onboarding; the unique constraint still exists.
- **AUTO-DECIDED — needs founder review:** the quota counts ACTIVE organizations the user **created**.

EXECUTE for `app_runtime`: `ensure_current_user(text, text)`, `update_my_profile(text, text)`,
`bootstrap_practice(text, uuid[], text, text)` only.

Ownership hand-over (FOUNDER-APPROVED, §8.3): the migration grants `app_authz`, `app_bootstrap`, `app_domain` and
`app_operator` to `CURRENT_USER` just before the hand-over, checks every EXECUTE grant made on their functions, and
revokes the memberships at the end of the file.

## 4. TypeScript

`src/domain` (pure, unit-tested):
- `errors.ts`: `mapDatabaseError({code, message, detail})` → `{status, code, reason?, message, details?}` for every
  SQLSTATE in spec §11 §3. PostgreSQL DETAIL is passed through only for PD-class errors and 23P01 (our JSON); for
  23xxx/22xxx it is dropped. Unknown codes → 500 `INTERNAL`.
- `permissions.ts`: `ROLES`, `PERMISSIONS` (same names as `app.role_permissions`).
- `locale.ts`: `LOCALES = ['hi','en']`, `resolveLocale({profile, cookie})` (profile wins after sign-in, then cookie,
  then `hi`).
- `idempotency.ts`: `isValidIdempotencyKey` (8–128 visible ASCII); `canonicalJson` (sorted keys, recursive).

`src/db` (the only place importing `postgres`; ESLint enforces it for `src/**`):
- `client.ts`: one lazily created `postgres(DATABASE_URL, { prepare: false, max: 3, idle_timeout: 20, connect_timeout: 10 })`.
- `tenant-tx.ts`: `withTenantTx(ctx, fn)`: one transaction; `set_config('app.actor_user_id', …, true)` and
  `set_config('app.tenant_id', …, true)`; when a tenant is given, probes `app.current_member_role()` and throws
  `DomainError` 404 if NULL; maps PostgreSQL errors with `mapDatabaseError`.
- `DomainError` class.
- **AUTO-DECIDED — needs founder review:** pool size `max: 3` per serverless instance.

`src/app/_lib` (server-only helpers, not routes):
- `auth.ts`: `verifyAccessToken(token)` with `jose.jwtVerify` against the remote JWKS (cached by jose), issuer
  `<url>/auth/v1`, audience `authenticated`, asymmetric algorithms only (ES256, RS256); returns
  `{actorId: sub, displayName}`, the name taken from `user_metadata.full_name`, else `.name` (strings only;
  FOUNDER-APPROVED §8.2).
- `context.ts`: `requireContext(req, {tenant})`: token from `Authorization: Bearer`, else from the Supabase session
  cookie; a cookie-authenticated write must be same-origin (FOUNDER-APPROVED §8.5); `X-Tenant-ID` (uuid) when the
  endpoint is tenant-scoped; `Idempotency-Key` when required.
- `http.ts`: `parseBody` requires `Content-Type: application/json` (FOUNDER-APPROVED §8.5); `handle(fn)` wrapper → error envelope `{"error": {code, reason?, message, request_id, details?}}`;
  `request_id` is a random UUID, logged with the code only (no PII). Zod errors → 422 `VALIDATION_FAILED` with
  `details.field`. Unknown errors → 500 logged with the request id.
- `request-hash.ts`: SHA-256 hex of `METHOD + path + canonicalJson(body)`; path relative to `/api/v1`.
- `supabase.ts`: `@supabase/ssr` server client whose cookies are forced `httpOnly`, `secure` (in production),
  `sameSite=lax`.

## 8. Founder review fixes (29 Oct 2026) — FOUNDER-APPROVED

1. **Harness first.** With `pd_migrator` holding `auth` privileges without GRANT OPTION (as Supabase's `postgres`),
   this migration's `GRANT … ON auth.users TO app_bootstrap` only warned and granted nothing, `m2_checks.sql` check 7
   failed and `ensure_current_user` failed with `permission denied for schema auth`. Confirmed before the fix below.
2. **No application role touches `auth`.** All `auth` grants are gone and `ensure_current_user` never reads
   `auth.users`. A new app user's `auth_user_id` FK to `auth.users(id)` proves the actor exists (the FK check runs
   with the rights of the table's owner); `foreign_key_violation` becomes PD401 `CONTEXT_MISSING`. The display name is
   a parameter filled from the verified JWT's `user_metadata` (`full_name`, else `name`), cleaned in SQL (control
   characters, zero-width space, bidi marks and overrides, whitespace runs → one space; ZWNJ/ZWJ kept for Devanagari;
   ≤ 120 characters; blank → NULL) and used only as display text.
   `m2_checks.sql` check 7 and a `03_bootstrap_identity.sql` test assert that no application role can use schema
   `auth` or read `auth.users`; tests prove the stored `raw_user_meta_data` is ignored.
3. **Membership only for the hand-over.** As in M1, the migration grants itself the function-owning roles
   (`app_authz`, `app_bootstrap`, `app_domain`, `app_operator`) right before the hand-over, because both the
   `ALTER FUNCTION … OWNER TO` statements and the schema-wide `REVOKE EXECUTE … FROM PUBLIC` need the owners' rights,
   then revokes them at the end; a DO block raises if any membership is left (`m2_checks.sql` check 14). Every
   EXECUTE grant on a function owned by another role is followed by a DO block that raises unless the grantee is in
   the ACL.
4. **Operator commands** (replace the FORCE-lift scripts).
   - Role `app_operator` (NOLOGIN, NOBYPASSRLS; created in M1 with the other roles).
   - Policies, all `TO app_operator`: SELECT on `organizations`, `app_users`, `org_members` (`USING (true)`);
     INSERT on `org_members` `WITH CHECK (role IN ('ADMIN','STAFF','READ_ONLY'))`; UPDATE on `org_members`
     `USING (role <> 'OWNER') WITH CHECK (role IN ('ADMIN','STAFF','READ_ONLY'))`. No DELETE.
   - Grants: column SELECT `organizations (id, name, status)` and `app_users (id, auth_user_id, status)` (no names);
     SELECT, INSERT and UPDATE `(role, status)` on `org_members`; EXECUTE on `raise_error` and `_ops_practice`.
   - `app._ops_practice(p_owner_user_id, p_practice_name) → uuid` (invoker): the ACTIVE practice of that name whose
     ACTIVE OWNER is that user; PD404 `PRACTICE_NOT_FOUND`, PD422 `PRACTICE_NAME_AMBIGUOUS`.
   - `app.ops_add_member(p_owner_user_id uuid, p_practice_name text, p_member_user_id uuid, p_role text) → jsonb`
     (SECURITY DEFINER, owner `app_operator`, `search_path = ''`): role must be ADMIN/STAFF/READ_ONLY (PD422
     `ROLE_NOT_ALLOWED`); the member must be an ACTIVE, attached app user (PD404 `MEMBER_NOT_SIGNED_IN`); the OWNER
     is never touched (PD422 `OWNER_UNTOUCHABLE`); inserts the membership or changes its role and re-activates it.
   - `app.ops_revoke_member(p_owner_user_id uuid, p_practice_name text, p_member_user_id uuid) → jsonb`: never the
     OWNER (PD422 `OWNER_UNTOUCHABLE`); ACTIVE → REVOKED, else PD404 `NOT_AN_ACTIVE_MEMBER`.
   - Both return `{org_id, user_id, role, status}` only. EXECUTE: the migration user only (`CURRENT_USER`, i.e.
     `postgres`); revoked from PUBLIC; no application role.
   - Scripts: one `SELECT app.ops_…(…)` each; e-mails are resolved in the script via `auth.users` (readable by
     `postgres`) and never printed.
   - Tests: `03_ops_members.sql` (25 assertions, including adds a member, refuses to touch the OWNER, app_runtime
     cannot execute) and `ops_smoke.sh` (the real script files, including "no e-mail in the output").
5. **CSRF.** `requireContext`: a cookie-authenticated request with a method other than GET/HEAD is refused with 403
   FORBIDDEN (reason `CROSS_ORIGIN_REQUEST`) unless `Sec-Fetch-Site` is `same-origin`, or, when the browser sends no
   `Sec-Fetch-Site`, `Origin` equals the request origin. Bearer requests are not checked. `parseBody` requires
   `Content-Type: application/json` (422 VALIDATION_FAILED, reason `JSON_REQUIRED`). `POST /auth/sign-out` applies
   the same origin check. Unit tests for each; an integration test for a `text/plain` body.
6. **Recorded for later, not fixed now** (`docs/plan.md` M12/M13): `idempotency_keys` has no customer link for
   erasure; `request_hash` is NOT NULL so it cannot be scrubbed; deleting the auth user leaves `app_users` ACTIVE
   instead of DELETED (spec §08 §1).
