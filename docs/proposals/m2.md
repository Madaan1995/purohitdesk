### Functions

| Function | Owner | Behaviour |
| --- | --- | --- |
| `app._slugify(text) → text` | migration user (invoker, IMMUTABLE) | lower-case ASCII letters/digits joined by `-`, ≤ 60 chars; `practice` when nothing ASCII remains (e.g. a Devanagari name) |
| `app._idem_begin(p_command, p_key, p_hash) → jsonb` | migration user (invoker) | NULL key → PD422 `IDEMPOTENCY_KEY_REQUIRED`; claims `(actor, key)` with `INSERT … ON CONFLICT DO NOTHING` inside the caller's transaction; on conflict: different command, hash or tenant → PD412 `IDEMPOTENCY_REUSE`, else returns the stored response with `idempotent_replay: true` |
| `app._idem_finish(p_key, p_result) → jsonb` | migration user (invoker) | stores the response, returns it with `idempotent_replay: false` |
| `app.ensure_current_user(p_locale text DEFAULT NULL) → jsonb` | `app_bootstrap` | needs an actor (PD401); existing row: refused with PD401 if the identity was deleted/detached, else returned; new row only if the actor exists in `auth.users` (else PD401), `display_name` from `raw_user_meta_data` `full_name`/`name` (trimmed, ≤ 120), `preferred_locale` = `p_locale` if valid else `hi`. Returns `{id, display_name, preferred_locale}` |
| `app.update_my_profile(p_display_name text, p_preferred_locale text) → jsonb` | `app_domain` | NULL argument = unchanged; validation PD422 with `details.field`; returns the same shape. No idempotency key (spec §05 §9) |
| `app.bootstrap_practice(p_name text, p_ceremony_type_ids uuid[], p_idem_key text, p_request_hash text) → jsonb` | `app_bootstrap` | see below |

`bootstrap_practice`, in order: actor required (PD401); a tenant in context → PD422 `VALIDATION_FAILED` (`field: tenant`);
the actor's app user must exist, be ACTIVE and linked (PD401); per-actor advisory lock; `_idem_begin` (replay returns);
name 1–120 chars (PD422 `field: name`); 1–20 distinct ceremony ids that exist (PD422 `field: ceremony_type_ids`);
at most 3 ACTIVE organizations created by the actor (PD429 `QUOTA_EXCEEDED`, `details.limit = 3`);
insert organization (slug from `_slugify(name)`; on collision retry with a random 6-hex suffix, up to 10 tries),
OWNER membership, the actor's priest profile if none exists (one per human; name = app user's display name, else
the practice name), BOOTSTRAP link (buffers 30/30), `org_sequences` row, one offering per chosen ceremony (both
names and default duration copied). Returns
`{organization: {id, name, kind, timezone, status, version}, role: "OWNER", organization_priest_id, offering_count}`.

- **AUTO-DECIDED — needs founder review:** slug collisions are resolved automatically (suffix) instead of returning
  409, because the slug is generated and not shown (revision 2.1 #17). The spec's older test "slug already taken →
  23505" therefore no longer applies to onboarding; the unique constraint still exists.
- **AUTO-DECIDED — needs founder review:** the quota counts ACTIVE organizations the user **created**.

EXECUTE for `app_runtime`: `ensure_current_user(text)`, `update_my_profile(text, text)`,
`bootstrap_practice(text, uuid[], text, text)` only.

## 4. TypeScript

`src/domain` (pure, unit-tested):
- `errors.ts`: `mapDatabaseError({code, message, detail})` → `{status, code, reason?, message, details?}` for every
  SQLSTATE in spec §11 §3. PostgreSQL DETAIL is passed through only for PD-class errors and 23P01 (our JSON); for
  23xxx/22xxx it is dropped. Unknown codes → 500 `INTERNAL`.
- `permissions.ts`: `ROLES`, `PERMISSIONS` (same names as `app.role_permissions`).
- `locale.ts`: `LOCALES = ['hi','en']`, `resolveLocale({profile, cookie})` (profile wins after sign-in, then cookie,
  then `hi`).
- `idempotency.ts`: `isValidIdempotencyKey` (8–128 visible ASCII); `canonicalJson` (sorted keys, recursive).

`src/db` (the only place importing `postgres`; ESLint enforces it for `src/**`):
- `client.ts`: one lazily created `postgres(DATABASE_URL, { prepare: false, max: 3, idle_timeout: 20, connect_timeout: 10 })`.
- `tenant-tx.ts`: `withTenantTx(ctx, fn)`: one transaction; `set_config('app.actor_user_id', …, true)` and
  `set_config('app.tenant_id', …, true)`; when a tenant is given, probes `app.current_member_role()` and throws
  `DomainError` 404 if NULL; maps PostgreSQL errors with `mapDatabaseError`.
- `DomainError` class.
- **AUTO-DECIDED — needs founder review:** pool size `max: 3` per serverless instance.

`src/app/_lib` (server-only helpers, not routes):
- `auth.ts`: `verifyAccessToken(token)` with `jose.jwtVerify` against the remote JWKS (cached by jose), issuer
  `<url>/auth/v1`, audience `authenticated`, asymmetric algorithms only (ES256, RS256); returns the `sub`.
- `context.ts`: `requireContext(req, {tenant})`: token from `Authorization: Bearer`, else from the Supabase session
  cookie; `X-Tenant-ID` (uuid) when the endpoint is tenant-scoped; `Idempotency-Key` when required.
- `http.ts`: `handle(fn)` wrapper → error envelope `{"error": {code, reason?, message, request_id, details?}}`;
  `request_id` is a random UUID, logged with the code only (no PII). Zod errors → 422 `VALIDATION_FAILED` with
  `details.field`. Unknown errors → 500 logged with the request id.
- `request-hash.ts`: SHA-256 hex of `METHOD + path + canonicalJson(body)`; path relative to `/api/v1`.
- `supabase.ts`: `@supabase/ssr` server client whose cookies are forced `httpOnly`, `secure` (in production),
  `sameSite=lax`.

Routes (`src/app/api/v1/…`), each validated with Zod (unknown fields rejected):

| Route | Body / headers | Response |
| --- | --- | --- |
| `GET /session` | — | `200 {user: {id, display_name, preferred_locale}, memberships: [{organization: {id, name, kind, timezone}, role, permissions: [...]}]}` |
| `PATCH /me` | `{display_name?, preferred_locale?}` | `200 {id, display_name, preferred_locale}`; also sets the `NEXT_LOCALE` cookie |
| `POST /onboarding/practice` | `{name, ceremony_type_ids: uuid[1..20]}`, `Idempotency-Key` | `201 {organization, role, organization_priest_id, offering_count, idempotent_replay}` (`200` on replay) |
| `GET /ceremony-types` | — | `200 {data: [{id, slug, name_en, name_hi, default_duration_min}]}` |
| `GET /organization` | `X-Tenant-ID` | `200 {id, kind, name, slug, timezone, plan, status, version}` + `ETag: "<version>"` |

- **AUTO-DECIDED — needs founder review:** all response shapes above (spec §11 names the endpoints only).
- **AUTO-DECIDED — needs founder review:** the API accepts the Supabase session cookie as well as a Bearer token,
  so the PWA's own pages can call it without exposing the token to JavaScript. Cookies are `SameSite=Lax`; all
  writes require a JSON body.
- `api/openapi.yaml`: OpenAPI 3.1 with these 6 operations (with `healthz`), `x-db-function`, `x-permission`,
  typed requests, responses and error envelope. **AUTO-DECIDED — needs founder review:** no machine validation of
  the OpenAPI file or response contract tests yet (the original consistency gates were not supplied; spec §13 §1
  says any replacement is proposed first).

Auth pages and flow (server-side PKCE, no Supabase client in the browser):
- `src/proxy.ts` (Next 16's renamed middleware): refreshes the Supabase session cookie on page and API requests;
  does nothing when the Supabase env vars are absent (local builds, healthz).
- `GET /auth/sign-in` → Supabase `signInWithOAuth({provider: 'google'})` → redirect to Google.
- `GET /auth/callback` → `exchangeCodeForSession` → `/`.
- `POST /auth/sign-out` → `signOut()` → `/sign-in`.

Pages (Hindi first; 16 px text, 44 px tap targets, 360 px wide):
- `/sign-in`: app name, "Sign in with Google", language toggle.
- `/onboarding`: practice name + ceremony picker (Hindi and English names, at least one), submit with an
  `Idempotency-Key` generated once per form, so a double tap or retry creates one practice; errors shown in the
  current language (quota, validation).
- `/` (home): current practice, **your role and its permissions** (localized labels), practice switcher (cookie
  `pd_tenant`, verified by RLS on every read), "Add another practice" (up to 3), language toggle, sign out.
- i18n: `next-intl` without routing; `src/i18n/request.ts` reads the `NEXT_LOCALE` cookie; after sign-in the home
  page syncs the cookie from `app_users.preferred_locale`. Catalogs `messages/hi.json`, `messages/en.json`.
- **AUTO-DECIDED — needs founder review:** cookie names `NEXT_LOCALE` (next-intl default) and `pd_tenant`.

## 5. Ops (`supabase/ops/`)

- `runbook.md`: give `app_runtime` LOGIN + password (generated by the founder, stored only in Vercel), build the
  Supavisor `DATABASE_URL`, disable Data API exposure of `app`, rotate the password, and step-by-step Supabase/Google
  setup (asymmetric JWT signing keys, Google OAuth client, redirect URLs incl. the Vercel preview wildcard).
- `add_member.sql` / `revoke_member.sql`: operator scripts for staging. The founder edits two values at the top
  (e-mail of a user who has signed in once, practice id) and runs the script as `postgres`. Because `org_members`
  has FORCE RLS, each script lifts FORCE inside its own transaction, writes one row, and restores FORCE before
  COMMIT (the table owner may always do this; nothing else changes).
- **AUTO-DECIDED — needs founder review:** the FORCE-lift technique for operator scripts (no new role, no policy
  for the owner, works whether or not Supabase's `postgres` has BYPASSRLS).

## 6. Tests (all AUTO-DECIDED — needs founder review)

SQL (`supabase/tests/03_bootstrap_identity.sql`): first login creates the app user (with locale); second call
returns it; actor not in `auth.users` → PD401; detached identity → PD401; bootstrap creates practice + the chosen
offerings as `app_runtime`; the new owner sees it under RLS; same key + same body replays the same org (one org
stored); same key + different body → PD412; one global priest profile across practices; slug generation and
collision suffix; Devanagari name → `practice…` slug; validation (empty name, no offerings, unknown or duplicate
ceremony) → PD422; inside a tenant context → PD422; 4th practice → PD429; missing key → PD422
`IDEMPOTENCY_KEY_REQUIRED`; 7-char key → 23514; a failed attempt frees the key; `update_my_profile` saves the locale
and rejects bad values; runtime cannot read or write `idempotency_keys`, `offerings`, `org_sequences` directly;
`app_bootstrap` cannot create an organization for someone else or link another person's profile (RLS); forged
tenant sees no offerings.

Domain unit tests: error mapping for every SQLSTATE in §11 §3 (and DETAIL dropped for 23505/23503/23514); canonical
JSON and request hash stable under key reordering; Idempotency-Key 8–128; locale resolution; JWT verification
rejects missing, malformed, expired, wrong-audience, wrong-issuer, wrong-signature and HS256 tokens (API-SEC-1) and
accepts a valid one.

Integration (`tests/integration/*.int.test.ts`, `npm run test:integration`, CI database job after `run.sh`): the real
route handlers against the throwaway database as a real `app_runtime` login through `postgres.js`: no token / bad
signature → 401; first `GET /session` creates the user; onboarding → 201, retry with the same key → same org;
`GET /organization` with own tenant → 200 + ETag; another practice's id → 404; revoked member → 404 on the next
request (API-SEC-3); `GET /ceremony-types` → 20; `PATCH /me` → locale saved.
